Keydock

Overview

A local-first macOS workspace that keeps developer identities separate, with protected storage, isolated browser sessions, and explicit consent before any sensitive action.

Technologies

RustmacOSIdentity isolationSecure storage

Problem and motivation

Developers routinely hold credentials for employers, clients, and personal accounts in one browser and one set of keys. Any extension or local process that reaches one of those sessions can often reach all of them.

Approach

Keydock gives each identity its own compartment. Sensitive data lives in a local encrypted vault that stays sealed until it is unlocked. Each identity opens in an isolated browser session, links are routed to the right identity by rule, and copied secrets are cleared from the clipboard automatically. Command-line and deep-link access pass through a consent prompt that names the process asking.

Technical design considerations

  • Compartments, not profiles. Identities are separated by design, not by user discipline.
  • Local first. Nothing depends on a cloud service.
  • Explicit, single-use consent. Every sensitive action requires an approval tied to that one action.

Security considerations

  • Threat model first. A written security model and threat model define what the design defends against and what it does not.
  • Local processes are not trusted by default. Requests from other programs must identify themselves and be approved.
  • Supply chain. Third-party dependencies are audited before they are adopted.

Outlook

Developer machines are a primary target because they hold the keys to everything else. Compartmentalizing identities on the device closes a gap that single sign-on and password managers leave open.
